## 4. 缺陷清單（severity 分類）

### <a id="h1"></a>[HIGH #1] `/healthz` 被 SPA catch-all 吃掉 — healthcheck 假綠 ✅ **已修**

**症狀**
```
$ curl -sS -o /dev/null -w '%{http_code} %{content_type}\n' \
  https://.../healthz
200 text/html; charset=utf-8         ← React SPA index.html

$ curl -sS -o /dev/null -w '%{http_code} %{content_type}\n' \
  https://.../health
200 application/json                 ← 真 API {"status":"ok"}
```

**衝擊**：我方 quadlet `HealthCmd` 打 `/healthz` → podman 永遠回報 healthy，即使 FastAPI 死了（因為 nginx / uvicorn 的靜態 fallback 還在服）。podman 也就永不會自動 restart 死掉的 server。

**Fix**（本 PR）：
- `quadlet/omnigent-server.container` `HealthCmd`
- `rootfs/usr/local/bin/omnigent-runner-loop` 等 server 就緒的 curl
- `scripts/install.sh` post-start 等待
- `tests/smoke-container.sh`、`tests/smoke-runner-dialin.sh`
- `README.md` + `README_zh-TW.md` 加警語

**Deploy 步驟**（部署到 `.197` 才生效）：
```bash
cd Woow_podman_omnigent_package
git pull
./scripts/install.sh          # 只 reinstall quadlets，OD_SKIP_BUILD=1 可省 build
systemctl --user restart omnigent-server
podman inspect omnigent-server --format '{{.State.Health.Status}}'  # 期待 healthy
```

### <a id="h2"></a>[HIGH #2] `POST /v1/sessions` 無 body size cap（upstream）

**症狀**：sub-agent 送 25 MB JSON body 到 `/v1/sessions`，server 完整 parse 後才因 `agent_id` 不存在回 404。→ 攻擊者送多 個 payload 可 amplifie memory。

**衝擊**：認證用戶（bearer）可觸發；未認證則被 401 擋。內網為主的部署衝擊小；若哪天把 server 直接開到 LAN/公網就是 pre-auth 剛好接不到、但 post-auth account 灑豆式 DoS 一條路。

**Fix 選項**（我方能加，但要小心不擋合理 payload 如 `/v1/imports`）：
1. **建議**：在前面加 nginx sidecar 設 `client_max_body_size 1m`（chat / config API）+ `10m`（imports/uploads）
2. **暫緩**：等上游修（觀察 open issue）

**現況**：本 PR **未加** nginx sidecar（不小心會擋 file upload / import 流）。已在 report 標記，等後續評估。

### <a id="h3"></a>[HIGH #3] Runner 的 pi harness 一直顯示 `needs-auth`（upstream #152 一致）

**症狀**：
- `/v1/hosts` API 回 `configured_harnesses: {pi: {status: "needs-auth", ...}, pi-native: {...}, native-pi: {...}}`
- 首頁警告 `Pi isn't configured on 6044bae34a59 — run omni setup on that machine.`
- Chat harness picker「Pi」旁掛「needs auth」標籤

**實測**：pi 明明可用 — 送 `Reply with exactly the word: e2e-ultracode-2026`，pi 用 `GPT-5.6 Sol` 正確回覆。auth 資訊經由 shared `pi-agent-data` volume 由 pi-web 那邊灌好。

**Root cause**：upstream bug #152 — omnigent 的 harness availability 只看 binary 是否在，不看 credentials 是否有效；我方 pi 的 credential 走 pi-agent volume 而非 omnigent 自己 tracks 的 `omni setup` 流程，omnigent 就判定為 needs-auth。

**Fix 選項**：
1. **cosmetic 蓋掉**：user 在 `/settings/appearance` 打開「Hide unconfigured harnesses」toggle
2. **runner-loop 加 `omni setup` 呼叫**：需研究 omni setup 的 headless 形式（互動式 CLI，可能要 stdin/expect）
3. **等上游修**：#152 open

**現況**：本 PR **未動**。在 README 加了「Hide unconfigured harnesses」的解決指引（後續 patch）。

**Fix**：upstream 問題，不動。

### <a id="m5"></a>[MED #5] Chat 頁對 `claude-native` / `codex-native` 反覆 500

**症狀**：每次進 chat 頁面 `/v1/hosts/{host_id}/harnesses/claude-native/model-options` 各噴 500，總共觸發 6-8 次（`take_screenshot` 網路面板可見）

**Root cause**：我方 runner 只帶 pi，server 對這兩個 harness 沒 config，`model-options` handler 沒優雅處理 → 500 而非 404。

**Fix 選項**：
1. **user 側 workaround**：`/settings/appearance` 開「Hide unconfigured harnesses」
2. **upstream 應改成 404**

**現況**：本 PR **未動 code**，僅在 README 加 workaround 指引。
